# 第 1 阶段代码与文件职责说明

本文用于帮助产品、数据和研发人员快速理解第 1 阶段新增文件分别承担什么工作，以及修改某项功能时应该从哪里开始。

## 1. 总体结构

```text
请求
  ↓
TriDict.HttpApi.Host        应用启动、鉴权、CORS、健康检查
  ↓
TriDict.HttpApi             HTTP 路由与参数绑定
  ↓
TriDict.Application         查询或业务用例编排
  ↓
TriDict.Domain              领域实体、规则和仓储接口
  ↓
TriDict.EntityFrameworkCore PostgreSQL 映射与仓储实现
```

`Domain.Shared` 和 `Application.Contracts` 位于主调用链两侧，分别提供各层共用的基础定义和对外服务契约。`DbMigrator` 独立执行数据库迁移，避免多个 API 实例同时修改数据库。

## 2. 根目录文件

| 文件 | 负责的工作 | 一般何时修改 |
|---|---|---|
| `TriDict.sln` | 汇总后端和测试项目，供 IDE、构建和 CI 使用 | 新增或移除项目时修改，优先使用 `dotnet sln` 命令 |
| `global.json` | 固定 .NET SDK 为 10.0.401，避免开发机使用不同 SDK | 团队统一升级 SDK 时修改 |
| `Directory.Build.props` | 为所有项目统一目标框架、C# 版本、可空检查和构建规则 | 需要统一编译策略时修改 |
| `Directory.Packages.props` | 集中锁定 ABP、EF Core、测试库等 NuGet 版本 | 升级或修复依赖漏洞时修改；项目文件内不要重复写版本号 |
| `README.md` | 项目入口说明，包含构建、测试、启动方式和服务地址 | 开发流程或服务入口变化时同步更新 |
| `.gitignore` | 排除 SDK、临时文件、构建产物、日志和本地秘密 | 产生新的本地文件类型时修改 |
| `.env.example` | Docker 环境变量模板，不保存真实密码 | 新增可配置基础设施参数时修改 |
| `Dockerfile` | 构建 API 和迁移程序两个容器镜像 | 发布运行时、入口程序或镜像版本变化时修改 |
| `.dockerignore` | 减少 Docker 构建上下文，避免把工具、输出和 Git 数据复制进镜像 | 构建上下文出现不必要文件时修改 |

`.tools/` 是项目内隔离的 .NET SDK 和辅助工具，`.tmp/` 是过程文件；二者都不是业务源代码，不应提交。

## 3. `TriDict.Domain.Shared`：全项目共享定义

该项目不包含数据库和 Web 依赖，负责最稳定、最基础的定义。

| 文件 | 职责 |
|---|---|
| `TriDictConsts.cs` | 数据库表名前缀、文本长度、语言标签长度等全局常量 |
| `TerminologyEnums.cs` | 发布状态、可靠性等级、术语类型等枚举 |
| `TriDictTextNormalizer.cs` | 查询文本规范化：兼容字符归一化、转小写、首尾和连续空白处理 |
| `TriDictDomainSharedModule.cs` | 声明 ABP 共享模块及其基础依赖 |
| `TriDict.Domain.Shared.csproj` | 该项目的 NuGet 依赖和构建入口 |

注意：文本规范化结果用于搜索，不覆盖词典中展示的原始词形。西班牙语重音、中文原文和专名大小写仍保存在 `Term.Text` 中。

## 4. `TriDict.Domain`：术语业务规则

这是最核心的业务层。它描述“系统中的事实是什么”和“允许怎样改变”，不关心 HTTP 或 PostgreSQL。

### 4.1 术语实体

| 文件 | 职责 |
|---|---|
| `Terminology/Concept.cs` | 概念聚合根；维护概念代码、领域、发布状态、可靠性、版本、术语和定义；执行提交审核、批准、发布等约束 |
| `Terminology/Term.cs` | 某个概念在指定语言中的表达；保存词形、规范化词形、词性、地区、首选状态、`SenseOrder` 和 `UsageContext` |
| `Terminology/Definition.cs` | 当前概念在指定语言和场景下的定义，可关联来源 |
| `Terminology/DomainCategory.cs` | 经贸、信息技术等领域及其层级、三语名称和排序 |
| `Terminology/IConceptSearchRepository.cs` | 定义应用层需要的检索能力，但不规定使用 PostgreSQL 还是 OpenSearch |

### 4.2 多义词如何隔离

同一个词形的不同意义必须建立不同 `Concept`。例如三个 `modelo` 义项会拥有三个概念代码；每个概念内部维护自己的三语术语和定义。`SenseOrder` 只负责词典页面排序，`UsageContext` 说明使用场景，两者都不能代替独立概念。

### 4.3 模块文件

| 文件 | 职责 |
|---|---|
| `TriDictDomainModule.cs` | 声明领域模块与 `Domain.Shared` 的依赖关系 |
| `TriDict.Domain.csproj` | 引用共享项目和 ABP DDD 领域包 |

业务规则应优先写在实体或领域服务中，不应只写在控制器、前端或数据库触发器中。

## 5. `TriDict.Application.Contracts`：对外服务契约

该项目定义调用者可以使用什么，不放具体实现。Web、UniApp、管理端和测试都可以围绕这些 DTO 与接口进行开发。

| 文件 | 职责 |
|---|---|
| `Dictionary/SearchDictionaryInput.cs` | 搜索输入模型和参数校验：查询词、源语言、领域、页码和页大小 |
| `Dictionary/DictionarySearchItemDto.cs` | 搜索响应结构；一个 DTO 对应一个独立概念义项 |
| `Dictionary/IDictionarySearchAppService.cs` | 词典搜索应用服务接口 |
| `Permissions/TriDictPermissions.cs` | 权限名称常量，避免在代码中散落字符串 |
| `Permissions/TriDictPermissionDefinitionProvider.cs` | 注册概念查看、创建、编辑、审核和发布权限 |
| `TriDictApplicationContractsModule.cs` | 声明契约模块与授权模块依赖 |
| `TriDict.Application.Contracts.csproj` | 契约项目依赖配置 |

如果只是增加响应字段，通常先修改 DTO；如果改变业务行为，还需要同步修改应用层、领域层、API 测试和 OpenAPI 契约。

## 6. `TriDict.Application`：用例编排

| 文件 | 职责 |
|---|---|
| `Dictionary/DictionarySearchAppService.cs` | 规范化用户查询，调用仓储，分页，并把每个 `Concept` 映射成独立搜索结果 |
| `TriDictApplicationModule.cs` | 声明应用模块对契约和领域模块的依赖 |
| `TriDict.Application.csproj` | 应用项目依赖配置 |

应用层可以协调多个仓储、权限和事务，但不应包含数据库专用 SQL，也不应直接返回 EF Core 实体。

## 7. `TriDict.EntityFrameworkCore`：PostgreSQL 数据访问

| 文件 | 职责 |
|---|---|
| `TriDictDbContext.cs` | 把概念、术语、定义和领域映射到 PostgreSQL 表，配置外键、长度和索引 |
| `EfCoreConceptSearchRepository.cs` | 实现领域层定义的检索接口；当前查询已发布概念并支持语言、领域、分页与义项排序 |
| `TriDictDbContextFactory.cs` | 供 `dotnet ef` 在设计阶段创建 DbContext，不需要先启动 API |
| `TriDictEntityFrameworkCoreModule.cs` | 注册 DbContext、默认仓储、专用搜索仓储及 Npgsql 提供程序 |
| `TriDict.EntityFrameworkCore.csproj` | EF Core、PostgreSQL 和设计工具依赖 |

### 7.1 `Migrations/` 目录

| 文件 | 职责 | 是否手工修改 |
|---|---|---|
| `20260923072318_InitialTerminologySchema.cs` | 首个迁移的 `Up` 和 `Down` 操作，创建四张核心表及索引 | 生成后可以评审，原则上不直接重写已执行迁移 |
| `20260923072318_InitialTerminologySchema.Designer.cs` | EF Core 为该迁移保存的模型元数据 | 不应手工修改 |
| `TriDictDbContextModelSnapshot.cs` | EF Core 当前模型快照，用于计算下一次迁移差异 | 不应手工修改 |

实体或映射变化后，应生成新的迁移，不能直接改生产数据库，也不能删除已经在共享环境执行过的迁移。

## 8. `TriDict.HttpApi`：HTTP 接口

| 文件 | 职责 |
|---|---|
| `Controllers/DictionaryController.cs` | 暴露 `/api/v1/dictionary/search`，完成查询参数绑定并调用应用服务 |
| `Controllers/SystemController.cs` | 暴露无敏感信息的系统版本接口，供联调确认服务身份 |
| `TriDictHttpApiModule.cs` | 注册 ABP MVC 与应用契约依赖 |
| `TriDict.HttpApi.csproj` | HTTP API 项目依赖配置 |

控制器应保持轻量：不直接访问 DbContext，不复制领域规则，也不把异常细节自行拼接成响应。

## 9. `TriDict.HttpApi.Host`：应用入口与运行管线

| 文件 | 职责 |
|---|---|
| `Program.cs` | 创建 WebApplication、加载 ABP 模块、初始化并启动服务；日志只启用控制台提供程序 |
| `TriDictHttpApiHostModule.cs` | 组合应用、API 和 EF Core 模块；配置 JWT、CORS、健康检查、OpenAPI 和中间件顺序 |
| `appsettings.json` | 默认连接串、身份服务、CORS 来源和日志级别 |
| `appsettings.Development.json` | 开发环境覆盖配置，如允许本地身份服务不使用 HTTPS 元数据 |
| `Properties/launchSettings.json` | IDE/`dotnet run` 的本地启动地址和环境变量 |
| `TriDict.HttpApi.Host.csproj` | Web 主机依赖和项目引用 |

真实密码、生产身份服务地址和证书不能直接写入这些文件，应通过环境变量或秘密管理服务提供。

## 10. `TriDict.DbMigrator`：数据库迁移入口

| 文件 | 职责 |
|---|---|
| `Program.cs` | 连接 PostgreSQL、执行所有待执行迁移，并初始化 ECON、IT、RES、CUL 四个一级领域 |
| `TriDict.DbMigrator.csproj` | 引用 EF Core 项目和主机基础库 |

部署顺序应为“数据库备份/检查 → 运行迁移程序 → 启动 API”。API 本身不调用 `MigrateAsync`，从而避免多个实例抢跑迁移。

## 12. 部署与 CI

| 文件 | 职责 |
|---|---|
| `deploy/docker/compose.yml` | 编排 PostgreSQL、Redis、迁移程序、API，以及可选 OpenSearch |
| `.github/workflows/backend-ci.yml` | 在推送和拉取请求中执行恢复、Release 构建、测试并上传测试结果 |

OpenSearch 当前通过 `search` profile 预留，只有进入检索阶段后才会增加索引投影、同步任务和实际搜索实现。

## 14. 常见需求应修改哪些位置

| 需求 | 首要修改位置 | 通常还需同步 |
|---|---|---|
| 新增概念业务规则 | `TriDict.Domain` | Domain.Tests、应用层、文档 |
| 新增查询参数 | Application.Contracts DTO | Application、HttpApi、Application.Tests、OpenAPI 测试 |
| 新增数据库字段 | Domain 实体、DbContext 映射 | 新迁移、DTO、测试、导入模板 |
| 新增 API | Application.Contracts、Application、HttpApi | Host 配置、HttpApi.Tests、API 文档 |
| 新增权限 | `TriDictPermissions` 与定义提供器 | 应用服务授权、身份角色映射、管理端 |
| 修改数据库连接 | 环境变量或 Host 配置 | DbMigrator、Compose、部署秘密 |
| 升级依赖 | `Directory.Packages.props` | 恢复、构建、全部测试、漏洞审计、迁移兼容性检查 |

判断放置位置的简单原则是：业务不变量放 Domain；用例步骤放 Application；输入输出形状放 Contracts；HTTP 细节放 HttpApi；数据库细节放 EntityFrameworkCore；运行环境组合放 Host。
